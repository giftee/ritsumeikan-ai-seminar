## Part 1 講義: ソフトウェアエンジニアの役割と、AIによる能力の増幅

### ソフトウェアエンジニアとは技術的な専門性を持って課題解決をする人

最初に、プログラマーとソフトウェアエンジニアの役割を比べます。実際の仕事では両者は大きく重なり、会社によって呼び方も異なります。ここで区別したいのは、優劣ではなく仕事の重心です。

大きく言うと、プログラマーは「コードを書く人」、ソフトウェアエンジニアは「技術的な専門性を持って課題解決をする人」です。

| 観点 | プログラマーとしての重心 | ソフトウェアエンジニアとしての重心 |
|---|---|---|
| 主な責務 | 仕様を正しくコードにする | 問題をソフトウェアで解決する |
| 起点 | 何を実装するか | 何を解決すべきか |
| 対象範囲 | 実装、テスト | 要件、設計、実装、運用、改善 |
| 良い仕事 | 正しく高品質なコードを書く | 適切な技術判断によって価値を生む |
| 意思決定 | 実装方法を判断する | ユーザー、事業、技術を踏まえて判断する |
| 他者との関係 | 与えられた仕様を実現する | プロダクトマネージャー（PdM）、デザイナー、営業などと仕様自体を作る |

コードを書くことは重要です。ただし、コードは目的ではなく、問題を解決するための手段の1つです。

```text
課題を知る
  -> 解くべき問題を決める
  -> 解決方法を選ぶ
  -> 設計して実装する
  -> 利用者へ届ける
  -> 運用し、結果から改善する
```

ソフトウェアエンジニアは、この流れ全体に関わります。実装する前にも、リリースした後にも仕事があります。

### 同じ依頼でも、考える範囲が違う

たとえば、「購入画面にクーポン機能を追加してください」と依頼されたとします。

プログラマーとしては、仕様を確認し、データベース、API、画面を実装し、テストを書くことが中心になります。

ソフトウェアエンジニアは、実装方法を考える前に、次のような問いも持ちます。

| 問い | なぜ考えるのか |
|---|---|
| そもそも何の課題を解決したいのか | 手段と目的を取り違えないため |
| クーポン機能が本当に最適なのか | より小さく効果的な方法があるかもしれないため |
| 既存の仕組みを再利用できないか | 開発と運用の負担を減らすため |
| 他の商品にも展開する可能性があるか | 将来の変更を踏まえて設計するため |
| 不正利用や問い合わせが増えないか | 利用者と運用担当者への影響を確かめるため |
| 効果をどう測るか | 作った後に課題が解決したか判断するため |

確認した結果、クーポンを作るより既存機能の案内を改善した方がよいと分かれば、「今回は作らない」と判断することもあります。多くのコードを書くことではなく、問題を適切に解決することがゴールだからです。

> プログラマーは、与えられた問題をコードで解く。ソフトウェアエンジニアは、解くべき問題そのものを見つけ、技術を使って解決する。

### 課題設定と技術判断を持つ人は、AIで10倍・100倍の成果を目指せる

課題設定ができ、技術的な意思決定を持てるエンジニアは、AIを単なるコード補完ではなく、自分の能力を増幅するレバレッジとして使えます。

AIに調査、実装案、テスト、文書化を任せれば、1人で順番に行っていた作業を短時間で進められます。複数の案を同時に作らせて比較したり、独立した作業を並行して進めたりすれば、1人のエンジニアが扱える仕事の量と範囲はさらに広がります。

```text
従来
  人が調査 -> 設計 -> 実装 -> テスト -> 文書化

AIを活用
  人が課題と判断基準を設定
    -> AIが調査・複数案・実装・テスト案を高速に作る
    -> 人が比較・判断・検証する
    -> 次の作業を複数のAIへ展開する
```

作業によっては、10倍の速さや、従来の100倍に相当する試行・成果物を扱える可能性があります。ここでの10倍・100倍は、すべての人や作業に対する保証ではありません。AIによって、エンジニア1人の影響力を桁違いに広げられる可能性を表しています。

この増幅を価値ある成果へ変えるには、AIへ何を任せ、どこで人が判断するかが重要です。

ただし、増えるべきものはコードの行数ではありません。より価値の高い課題を、より短い時間で、より高い品質で解決できることが生産性です。

```text
価値ある成果
  = 課題設定
  x 技術的な意思決定
  x AIの実行力
  x 人による検証
```

AIの実行力だけが大きくても、課題設定が間違っていれば、間違った方向へ10倍速く進みます。設計判断や検証が弱ければ、大量のコードと大量の不具合が同時に生まれます。

だからこそ、AI時代には次の能力が重要になります。

| 能力 | AIの生産性を引き出す理由 |
|---|---|
| 課題設定 | 解く価値のある問題へAIの実行力を向ける |
| 分解 | 大きな課題を、AIが扱えて人が確認できる単位にする |
| 技術判断 | 複数の設計案から、制約に合うものを選ぶ |
| 検証 | もっともらしい誤りや副作用を見つける |
| 学習 | 成功と失敗を次の指示や開発ルールに反映する |

> AIがエンジニアを置き換えるのではなく、課題設定と技術判断を持つエンジニアが、AIを使って影響力を大きくする。

## Part 2 講義: 個人でAIと協働する型

では、AIの実行力を価値ある成果へ変えるために、実務ではどのようにAIと協働すればよいのでしょうか。

### AIは、正解を知らない

生成AIは、コードの案をすばやく作り、修正方法やテスト項目を提案できます。一方で、利用者が何を必要としているのか、どの制約を守るべきか、どこまで変更してよいのかは、伝えなければ分かりません。

AIは、情報が足りないときにも作業を止めるとは限りません。足りない部分を推測で補い、もっともらしい答えを返すことがあります。そのため、流暢な説明や動きそうなコードを、そのまま正解だと考えることはできません。

AIは「答えを受け取る相手」ではなく、「目的と条件を共有し、途中で確認しながら一緒に作業する相手」として扱います。

### 人は「何を作るか」と「採用してよいか」を判断する

AIに実装を手伝ってもらっても、次の判断は人間が受け持ちます。

| 人間が考えること | 具体的な行動 |
|---|---|
| 目的 | 利用者が必要とする状態を言葉にする |
| 文脈 | 関連する仕様、コード、これまでの経緯を渡す |
| 制約 | 守る条件、変更範囲、今回はしないことを決める |
| 検証 | 正常時、境界、失敗時の確認方法を決める |
| 採用判断 | AIの案を進めるか、修正させるか決める |
| 学習 | 見落とした観点を次回のAI指示に加える |

AIが得意なのは、与えられた目的や条件に沿って案を作ることです。人間が担うのは、その目的や条件を決め、案を採用してよいか判断することです。

### 実務では、確認地点を置きながらAIと協働する

良い依頼とは、長いプロンプトを書くことではありません。目的を伝え、AIの理解を確認し、計画を直し、結果を検証する対話を作ることです。

| ステップ | 人が行うこと | AIに依頼すること |
|---|---|---|
| 1. Frame | 課題、目的、成功条件、範囲外を決める | 理解した内容と不明点を説明させる |
| 2. Context | 関連コード、仕様、制約、過去の経緯を渡す | 必要な追加情報を挙げさせる |
| 3. Plan | 変更方針と確認方法を判断する | 実装前に計画、選択肢、テスト方針を出させる |
| 4. Execute | 確認できる小さな単位を指定する | 合意した範囲だけを実装させる |
| 5. Verify | 差分、テスト、利用者への結果を確認する | テストや懸念点を提示させる |
| 6. Learn | 見落としと有効だった指示を残す | 次回の確認項目を整理させる |

実務では、一度に大きな変更を完成させようとせず、PlanとVerifyを確認地点にします。AIが出したコード、テスト、説明はすべて候補であり、確認せずに採用する完成品ではありません。

AIに任せやすいのは、調査、比較案、下書き、反復作業です。人が持ち続けるのは、目的、優先順位、トレードオフ、品質基準、最終的な採用判断です。

AIには調査、候補作成、実装などの手続きを任せられます。ただし、目的の設定と、次へ進めてよいかという判断は人が持ちます。

> AIに手続きを渡す。判断は人が持つ。

## Part 3 ハンズオン: 個人としてAIと協働する

### 使うリポジトリ

https://github.com/giftee/ritsumeikan-ai-seminar

前半と後半で、見る場所が変わります。

| パート | 見るもの | 目的 |
|---|---|---|
| 個人でのAI協働 | 教材画面、対象コード、AIの返答 | AIへ文脈を渡し、計画を判断する |
| チームでのAI協働 | Issue #1、Pull Request #2、Files changed、Checks | 判断材料を共有し、変更をレビューする |

ローカル環境とエディタ・CLIのAIツールがある人は、実装から検証まで手元で試せます。準備がない人も、講師の画面で同じ流れを見ながら、判断の練習にはすべて参加できます。BranchやCommit、GitHubへのpushは行いません。

### 1. Frame: 題材と現在の問題を認識する

ここからハンズオンです。今回の題材は、研究室・サークルの差し入れeギフト推薦です。発表会後や作業会後に、予算や好みに合わせて差し入れを選ぶ場面を想定します。

講師が画面を見せます。ローカル環境がある人は、次のURLで確認できます。

```text
http://127.0.0.1:5173/
```

`main` ブランチでは、研究室条件の初期表示で `コンビニスイーツ` が推薦され、画面上に `要レビュー` と表示されます。

これは、避けたいカテゴリに入っている `コンビニ` が推薦されてしまっているためです。

参考: 何も整理せずに書いた依頼文の例が `prompts/bad-prompt.md` にあります。「いい感じにして」という依頼は、決まっていないことのすべてをAIの推測に委ねる依頼です。

### 2. Frame: 分かっていることと、決まっていないことを分ける（目安: 3分）

実務でAIに作業を任せるとき、最初に必要なのは「何が決まっていて、何が決まっていないか」を見極めることです。決まっていないことに気づかないままAIに依頼すると、AIはそこを推測で埋めて、もっともらしいコードを返します。

画面とコードから分かることを整理してください。

- 研究室条件で、避けたいカテゴリ（コンビニ）の `コンビニスイーツ` が推薦され、`要レビュー` と表示されている
- 予算と在庫はすでに考慮されているように見える
- 対象は `src/giftRecommendation.js`。既存テストは候補なしの1件だけ

作業メモ:

```markdown
## 画面とコードから分かっていること

## 決まっていないこと（実装前に決める必要があること）

## 自分ならこう決める（仮決め）
```

考える観点のヒント:

- 条件を満たす候補が複数残ったら、どれを選ぶのか
- 好みに1つも合わないギフトしか残らなかったら、どうするのか
- 同じくらい良い候補が並んだら、何で決めるのか
- どのファイルまで変更してよいのか

### 3. AIへ依頼し、AIと人の認識の違いを見つける（目安: 3分）

AIに頼むときは、いきなり実装させません。まず、仕様の理解、決まっていない点、修正方針、追加すべきテストを出してもらいます。

次のテンプレートを使い、あなたが手順2で書いた「分かっていること」「決まっていないこと」を反映してください。

````markdown
推薦ロジックを直したいです。まず実装せず、次を出してください。

1. 仕様の理解
2. 仕様として決まっていない点（推測で決めず、質問として列挙する。各質問には選択肢と、あなたのおすすめを添える）
3. 修正方針の案
4. 追加すべきテストの案

決まっていない点を勝手に決めて実装方針にしないでください。まず質問として出してください。

## 現在の問題

研究室条件で、避けたいカテゴリ（コンビニ）のギフト `コンビニスイーツ` が推薦されてしまう。

## 分かっていること

- 前の手順で分かったこと
````

返答が来たら、分かっていることと分かっていないことが AI と自分が調査したものを見比べてください。AIはすべてを質問できるとは限りません。

### 4. Plan Gate: この計画を通してよいか判断する（目安: 2分）

AIが出した修正計画のサンプルを見ます（`prompts/sample-ai-plan-for-plan-gate.md`）。

このサンプルには、実務でよく起きる問題がいくつか仕込まれています。`prompts/plan-gate-checklist.md` の観点で、実装に進めてよいかを判断してください。

チェックリスト:

| 観点 | 見ること |
|---|---|
| 目的 | 依頼の目的とずれていないか |
| 範囲 | 変更対象を広げすぎていないか |
| 決まっていない点 | 勝手に決めず、質問として出しているか |
| テスト | 直したい問題を再現・防止するテストが含まれているか |
| 範囲外 | 頼んでいない機能を勝手に追加していないか |

判断メモ:

```markdown
判断: 進めてよい / まだ進めない

理由:

このAIが「勝手に決めていたこと」:
```

書けたら、同じ観点で自分のAIの返答も見直してください。

### 5. まず、正しい挙動を再現したテストだけを書かせる（目安: 2分）

計画がPlan Gateを通っても、いきなり実装はさせません。実務では、直す前に「壊れていること」をテストで証明します。

```text
実装はまだしないでください。まず、正しい挙動を再現するテストを1つだけ
test/giftRecommendation.test.js に追加してください。
避けたいカテゴリ（convenience_store）のギフトが推薦されないことを確認するテストです。
```

テストが追加されたら、自分のターミナルで `npm test` を実行してください。

**新しいテストが落ちれば成功です。** 落ちた＝現在のコードのバグを、テストが捕まえられた証拠です。もし通ってしまったら、そのテストはバグを再現できていません。AIは、一見それらしいのに何も検証していないテストをよく書きます。一度も落ちるところを見ていないテストは、何も証明していません。

### 6. 実装を依頼し、生成を待つ間に課題そのものを疑う（目安: 1分）

赤くなったのを確認したら、実装に進みます。

```text
計画の通りに実装してください。さきほど追加したテストを含めて、
npm test がすべて通る状態にしてください。
```

チャット型AIの人は、修正後のコードを出してもらうところまでで構いません。ローカル環境がない人は、講師の画面で同じ流れを見てください。

AIがコードを生成している待ち時間に、1つだけ考えてください。

> そもそも、ギフトを「1つに絞って推薦する」ことは正しいのでしょうか。候補を3件見せて人が選ぶ方が、利用者の目的に合うかもしれません。あなたなら、実装の前に依頼者へ何を確認しますか。チャットに1行で書いてください。

正解はありません。Part 1の「解くべき問題を決めるのはエンジニア」を、AIの待ち時間で実践します。実務では、AIが実行している間こそ、人が課題を考える時間です。

### 7. 赤が緑になったことと差分を検証し、元に戻す（目安: 3分）

AIの実装が終わったら、「動いた」で終わらせずに検証します。

1. `npm test` を自分のターミナルで実行する。AIの「テストが通りました」という報告を、そのまま信じない。手順5で落ちたテストが、今度は通っている（赤→緑）ことを自分の目で確認する
2. `git diff` で差分を読む。実装の差分とテストの差分を分けて読み、決まっていなかった点（同点のときの決め方など）をAIがどう扱ったかを確認する
3. 画面（ http://127.0.0.1:5173/ ）で、研究室条件の推薦結果がどう変わったかを見る

確認できたら、変更を元に戻します。

```bash
git restore .
```

戻す理由は2つあります。1つは、後半で講師が用意したPR #2を、先入観のない目でレビューするため。もう1つは、AIの成果物は捨てても惜しくない速さで作り直せると体感するためです。差分を読み、良ければ採用し、迷えば捨てる。この判断の軽さが、AIネイティブ開発のリズムです。

### 実務の判断基準（持ち帰り用）

今日の流れの背後にある、実務でよく使う判断基準です。

- AIの「できました」「テストが通りました」は、自分の環境で再確認する
- テストは、落ちるところを見てから信じる。一度も落ちていないテストは何も証明していない
- 差分が一目で追えない大きさになったら、受け入れずに依頼を分割してやり直す
- 3往復直させてもずれ続けるなら、会話の中で粘らず、依頼文と渡すコンテキストを直して最初からやり直す
- 迷ったら捨てる。生成は安く、レビューは高い
- AIへの回答が曖昧だと、AIはまた推測で埋める。「場合による」と答えるなら、どの場合かまで決めて返す
- 重要な合意をチャット履歴に置き去りにしない。Issue、テスト、AGENTS.md などのファイルに固定した合意だけが、明日の自分と、隣の人のAIに引き継がれる

### 8. 個人でのAI協働を振り返る

AIとの対話を見返し、次をメモしてください。

```markdown
自分が「決まっていない」と気づけた点:

AIが質問してくれた点 / 推測で埋めていた点:

人が決めなければならなかったこと:

自分の仮決めや判断を、チームの誰もが参照できる場所に残すとしたらどこか:
```

最後の項目が、個人のAI活用をチーム開発へつなぐ入口です。あなたが今仮決めした「同点のときの決め方」は、隣の人の仮決めと同じとは限りません。それをどう揃えるかが後半のテーマです。

## Part 4 講義: チーム開発の大切さと、AI協働の型

### 早く行くことと、遠くまで行くこと

チームで働く意味を表す言葉があります。

> 早く行きたければ一人で行け。遠くへ行きたければみんなで行け。

一人で進めると、相談や調整をせず、すぐに決めて動けます。小さな試作や短期間の検証では、その速さが大きな強みになります。

一方で、実際のソフトウェアは、作って終わりではありません。多くの利用者に使われ、機能が増え、障害に対応し、何年も変更され続けます。最初は一人で理解できる大きさでも、価値が増えるほど、一人の知識と時間だけでは支えられなくなります。

### AI時代にも、チームの重要性は変わらない

AIを使えば、一人のエンジニアが以前より速く、多くの仕事を進められます。しかし、個人が速くなることと、プロダクトが長期的に成功することは同じではありません。

| AIによって起きること | チームで必要になること |
|---|---|
| 作られるコードや提案が増える | 目的に合うものを選び、品質を確認する |
| 複数の作業を並行できる | 変更同士の衝突や全体設計の一貫性を保つ |
| 一人で広い範囲を変更できる | セキュリティ、運用、利用者への影響を異なる視点で確認する |
| AIとの対話に多くの判断が含まれる | 判断の理由を共有し、別の人が引き継げるようにする |
| 実装速度が上がる | 何を作らないか、どこで止めるかをチームで判断する |

AIは一人を速くします。チームは、その速さを継続的な価値へ変えます。AI時代だからチームが不要になるのではなく、作れる量と速度が増えるからこそ、方向、品質、継続性を支えるチームが重要になります。

### チームでAIと協働するときの土台は、コンテキストの共有

AIは、チームの目的、利用者、過去の判断、暗黙のルールを自動では知りません。人は会話や経験から背景を補えますが、AIが使えるのは、その場で渡された情報と、参照を許可されたコードや文書だけです。

同じチームでも、人によってAIへ渡す情報が違えば、AIは異なる前提で実装します。ある人のAIは既存設計を守り、別の人のAIは同じ仕組みを作り直すかもしれません。個人では速くても、変更を組み合わせたときに一貫性が失われます。

そのため、チームでAIを使うときの最も重要な土台は、共通のコンテキストです。

| コンテキスト | AIとチームが知るべきこと | GitHub上の置き場所 |
|---|---|---|
| 目的 | 誰の、どの課題を、なぜ解決するのか | Issue |
| 完了条件 | 何を満たせば完成と言えるのか | Issue、テスト |
| ドメイン | 用語、利用者、業務上のルール | README、`docs/` |
| 技術 | アーキテクチャ、責務の境界、既存のインターフェース | コード、設計文書 |
| 開発ルール | コーディング規約、変更可能な範囲、禁止事項 | README、リポジトリのAI向け指示 |
| 品質基準 | 必要なテスト、性能、セキュリティ、運用条件 | Tests、Checks、文書 |
| 判断履歴 | 何を選び、何を選ばなかったか、その理由 | Pull Request、Review、設計記録 |

コンテキストを共有するとは、長いチャット履歴を全員へ配ることではありません。必要な情報を、チームが更新でき、AIも参照できる場所へ、構造化して残すことです。

```text
個人の頭やAIチャットにある情報
  -> Issue、コード、テスト、文書、PRへ残す
  -> 人とAIが同じ前提から作業する
  -> 判断と学びを次の変更でも再利用する
```

GitHubはコードの保管場所だけではありません。目的、技術的な前提、変更、検証結果、採用判断をつなぎ、人とAIが同じ根拠を参照するための場所です。

### コンテキストを共有するだけでは足りない

正しいコンテキストを渡しても、AIは誤ることがあります。また、生成される変更が大きすぎれば、人が十分に確認できません。共通のコンテキストを、チームが判断できる成果へ変える仕組みが必要です。

```text
チームでのAI協働
  = 共通のコンテキスト
  x レビューできる小さな変更
  x 再現可能な検証
  x 人による判断
  x 学びの更新
```

個人がAIをうまく使うだけでは、チーム全体の生産性は上がりません。個人のチャットにある文脈、判断、学びを、チームが再利用できる開発の仕組みに変える必要があります。

### コンテキストをチームの成果へ変える型

| 実務の原則 | 具体的に行うこと |
|---|---|
| 共通の文脈を持つ | 目的と完了条件はIssue、開発ルールはリポジトリの文書へ置く |
| AIの作業を小さくする | 1つのPRに目的を1つ置き、人が追える差分にする |
| 判断を記録する | 採用した案、採用しなかった案、理由をPRへ残す |
| 検証を再現可能にする | テスト、CI、確認手順を、別の人も実行できる形にする |
| 人のGateを置く | 計画とマージの前に、人が目的、リスク、品質を判断する |
| 学びをチームへ戻す | Reviewの気づきをテンプレートやAIへの共通指示へ反映する |

重要な仕様や判断をAIとのチャットだけに残してはいけません。チャットは作業場所、GitHubはチームの記録と判断の場所として使い分けます。

この考え方を、GitHub上の流れにすると次のようになります。

| ステップ | 人が担う判断 | GitHubとAIの使い方 |
|---|---|---|
| 1. Intent | 何を変えたいか | Issueに背景と目的を書く |
| 2. Requirements | 何を満たせば完成か | 制約と完了条件を明文化する |
| 3. Plan Gate | その方針で進めてよいか | AIに計画を出させ、人が確認する |
| 4. Small Change | 確認できる大きさか | Branchと小さな差分に分ける |
| 5. Verify | 何を確認できたか | テスト、画面、CIで検証する |
| 6. Share | 他の人が判断できるか | PRに理由と確認方法を書く |
| 7. Gate | 採用してよいか | Reviewで判断する |
| 8. Learn | 次回はどう改善するか | 学びをコメントやチームの指示に残す |

実装後に目的のずれを見つけるより、IssueやPlan Gateで見つけた方が小さな手戻りで直せます。AIで実装が速くなるほど、実装前後の確認地点を意識して作ることが重要です。

この型は、教材のために単純化した理想論ではありません。たとえばAWSが公開している開発メソドロジー [AI-DLC（AI-Driven Development Life Cycle）](https://github.com/awslabs/aidlc-workflows) は、要件分析から実装までの各段階に人の承認ゲートを置き、AIには決まっていない点を選択肢付きの質問として出させ、質問と回答をすべてファイルとして監査証跡に残し、開発ルールをリポジトリに置いてAIに読み込ませます。今日のPlan Gate、AGENTS.md、Issueの完了条件は、実務で使われているメソドロジーの最小構成です。

## Part 5 ハンズオン: GitHubを用いたチーム開発を実践する

ここからは、あなたがこのPRのレビュアーです。講師が用意したPR #2は、CI（自動テスト）が通っています。このパートの最後に、**Approve か Request changes を、理由1行とともにチャットで表明**してもらいます。

問いはこれだけです。

> CIが緑のPRを、あなたはそのままマージしてよいですか。

### 1. Issueで、前半の仮決めを答え合わせする（目安: 2分）

Issue #1:

https://github.com/giftee/ritsumeikan-ai-seminar/issues/1

前半で「決まっていない」と整理した点が、Issueの完了条件でどう決められているかを確認してください。候補の並び順、同点のときの決め方、候補なしの扱いは、あなたやAIの仮決めと同じでしたか。

```markdown
自分やAIが推測で決めていたことのうち、Issueが決めていたこと:

AIの計画から抜けていたこと:

Issueを読んで初めてチームで共有できたこと:
```

実務では、Issue本文の症状だけでなく完了条件まで読みます。症状は問題の一部であり、完了条件がチームのゴールだからです。

### 2. Pull Request #2 を読む（目安: 5分）

PR #2:

https://github.com/giftee/ritsumeikan-ai-seminar/pull/2

このPRは、講師が用意したレビュー用のPRです。GitHub Actionsのテストは通っています。ただし、完全な模範解答として読むのではなく、チームとして受け入れてよいかを判断します。

実務での基本的な読む順番:

1. Issueで目的と完了条件を確認する
2. Conversationで変更理由と確認方法をつかむ
3. Files changedで実装差分を読む
4. Files changedでテスト差分を読む
5. Checksで自動テストの結果を確認する
6. Reviewで質問、修正依頼、採用判断を残す

深く読み始める前に、Checksが失敗していないかだけは先に確認します。失敗している場合は、レビューを止めるのではなく、失敗内容が今回の変更と関係するかを確認します。

#### Conversationで変更の地図をつかむ

| 観点 | 見ること |
|---|---|
| Issue連携 | `Closes #1` でIssueと紐づいているか |
| 変更理由 | なぜ直す必要があるかが書かれているか |
| 確認方法 | `npm test` やGitHub Actionsで何を確認したかが分かるか |
| レビュー観点 | レビュアーが何を見るべきかが書かれているか |
| 不安点 | 残っている不安や範囲外が説明されているか |

#### Files changedで実装とテストを分けて読む

| ファイル | 見ること |
|---|---|
| `src/giftRecommendation.js` | Issueの仕様どおりに候補を絞り、並べ替えているか |
| `test/giftRecommendation.test.js` | 完了条件を確認するテストが追加されているか |

コードの書き方だけを見るのではなく、Issueの各条件が実装とテストの両方に現れているかを対応づけます。

| Issueの条件 | 実装にあるか | テストにあるか |
|---|---|---|
| 予算内 |  |  |
| 在庫あり |  |  |
| 避けたいカテゴリを除外 |  |  |
| 好みタグに一致 |  |  |
| 一致数が同じなら安い順 |  |  |
| 候補なしの表示 |  |  |

実装に処理があっても、テストがなければ将来の変更で壊れたことを検知しにくくなります。テストに項目があっても、期待値が仕様を正しく表しているかは人が読みます。

#### Checksで機械的な確認結果を見る

GitHub Actionsの `test` が成功しているか、何のコマンドが実行されたかを確認します。成功していても、上の対応表に空欄があれば、必要なテストが不足している可能性があります。

確認メモ:

```markdown
## 実装差分で確認したこと

## テスト差分で確認したこと

## 足りないと思ったこと
```

### 3. 画面上の結果も確認する（目安: 1分）

PR #2の修正後ブランチでは、同じ条件で `カフェチケット` が推薦され、`条件OK` と表示されます。

コードとテストだけでなく、利用者に見える結果が目的に合っているかも確認します。実務では、変更の種類に応じて画面確認、APIレスポンス、ログなど、利用者に近い地点での確認を選びます。

### 4. 任意: AIにレビュー補助をさせる

エディタ・CLIのAIツールがある人は、`prompts/ai-review-prompt-template.md` を使って、AIに確認漏れの候補を出させてください。テンプレート冒頭の「事前準備」に、PRの差分をAIに渡す方法（`git fetch origin pull/2/head:pr-2` — 読み取り専用でpushはしません）が書いてあります。環境がない人は飛ばして構いません。

見るポイントは1つです。あなたが対応表で見つけた空欄に、AIも気づきましたか。あなただけが気づいた観点、AIだけが気づいた観点はどれですか。実装と同じで、レビューでもAIの指摘は候補にすぎません。採用するかはレビュアーが判断します。

### 5. Reviewコメントを書き、判断を表明する（目安: 4分）

あなたがレビュアーとして、GitHub Reviewに書くつもりでコメントを書いてください。

実務で役立つReviewコメントには、次の特徴があります。

- どの仕様に対するコメントかが分かる
- 問題になる入力と期待する結果が具体的である
- なぜマージ前に必要なのかを説明している
- 今回のIssueと関係しない改善を混ぜない
- 最後にApprove / Request changesの判断がある

コメントの目的も区別します。

| 種類 | 使う場面 |
|---|---|
| Blocker | 仕様違反、バグ、必要なテスト不足。マージ前に修正が必要 |
| Question | 意図や前提を確認したい |
| Suggestion | 今回必須ではない改善案 |
| Good | 良い判断や、今後も残したい実装を伝える |

```markdown
### 良いと思ったこと

### 確認したいこと

### 追加してほしいこと

### 判断

Approve / Request changes
```

書けたら、チャットに判断を投稿してください。

```text
Approve（または Request changes）: 理由を1行
```

`reviews/` の模範解答は、まだ開かないでください。全員の判断が出そろったら、講師が集計して、模範コメントを画面で開きます。CIが緑でも判断が割れたなら、その割れ目にこそ、人がレビューする理由があります。

## 持ち帰りチェックリスト

AIにコードを書かせる前:

- 目的を説明した
- GitHub Issueや関連ファイルを渡した
- 分かっていることと、決まっていないことを分けた
- 決まっていないことを、推測で埋めず質問として出すよう依頼した
- 今回やらないことを書いた
- まず実装せず、修正方針とテスト方針を出すよう依頼した
- バグ再現テストを先に書かせ、落ちることを確認してから実装させた

PRを見るとき:

- Issueと紐づいている
- 差分が小さい
- PR本文に「何を変えたか」「なぜ変えたか」「どう確認したか」がある
- GitHub Actionsが通っている
- 必要なテストが足りている
- ユーザーに見える結果として妥当
- 次回AIに渡す学びが残っている

## 今日のまとめ

| 視点 | 持ち帰ること |
|---|---|
| ソフトウェアエンジニア | コードを書く前に、解くべき課題と技術的な方針を決める |
| AIによる能力の増幅 | 課題設定、分解、技術判断、検証によってAIの実行力を価値へ変える |
| 個人としてAIを使う | 目的と制約を渡し、理解、計画、結果を人が確認する |
| チームとしてAIを使う | Issue、PR、テスト、CI、Reviewに判断材料を残す |

AIは実行を速くし、扱える仕事の量と範囲を広げます。ただし、目的、制約、確認方法、採用判断は自動では持ちません。課題設定と技術判断を人が持ち、GitHubを使うことで、個人とAIの作業をチームが理解し判断できる成果に変えられます。

今日持ち帰ってほしいこと:

> 課題設定と判断は人が持つ。AIで実行力を増幅し、GitHubでチームの力に変える。

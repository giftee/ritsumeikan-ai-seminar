# AIネイティブ開発で、人間は何をするのか

GitHubと生成AIで学ぶ、チームで前に進める開発の型

## 今日のゴール

このハンズオンでは、AIにコードを丸投げするのではなく、AIの出力をGitHub上でチームが判断できる形にする練習をします。

題材は、研究室・サークルの差し入れeギフト推薦です。発表会後や作業会後に、予算や好みに合わせて差し入れを選ぶ場面を想定します。

今日の問い:

> AIがコードを書けるようになったら、人間のエンジニアは何をするのか？

今日の答え:

> 人間は、目的を決め、文脈を渡し、AIの出力を確かめ、GitHub上でチームが判断できる形にする。

## 1. まず教材画面を見る

講師が画面を見せます。ローカル環境がある人は、次のURLで確認できます。

```text
http://127.0.0.1:5173/
```

`main` ブランチでは、研究室条件の初期表示で `コンビニスイーツ` が推薦され、画面上に `要レビュー` と表示されます。

これは、避けたいカテゴリに入っている `コンビニ` が推薦されてしまっているためです。

PR #2 の修正後ブランチでは、同じ条件で `カフェチケット` が推薦され、`条件OK` と表示されます。

ここで大事なのは、次の2つを両方見ることです。

- テストが通っているか
- ユーザーに見える結果として妥当か

## 2. Issue #1 を読む

Issue #1:

https://github.com/giftee/ritsumeikan-ai-seminar/issues/1

Issueには、次の仕様が書かれています。

- 予算内のギフトだけを候補にする
- 在庫ありのギフトだけを候補にする
- 避けたいカテゴリのギフトは候補にしない
- 好みタグに1つ以上一致するギフトだけを候補にする
- 好みタグの一致数が多い順に選ぶ
- 一致数が同じなら安い順に選ぶ
- 候補がなければ `おすすめできるギフトがありません` を返す
- 外部API連携、個人情報保存、AIによる自由文メッセージ生成は今回の範囲外

作業メモ:

```markdown
## 目的

## 守るべき仕様

## 今回変更してよい範囲

## 今回やらないこと

## 完了条件
```

注意すること:

Issue本文の症状は「好みに合わないギフトが選ばれる」ことに見えます。ただし、完了条件には予算、在庫、除外カテゴリ、好みタグ一致数、同点時の安い順まで含まれています。

症状説明だけで判断せず、完了条件まで見てください。

## 3. 悪いAI依頼文を読む

次の依頼文を見てください。

```text
研究室向けに、いい感じの差し入れギフトをおすすめするようにして。
```

この依頼文の問題点を書いてください。

```markdown
1.
2.
3.
```

ヒント:

- 何を直すべきかが明確か
- 守るべき制約が書かれているか
- 変更してよい範囲が書かれているか
- どう確認するかが書かれているか
- AIにいきなり実装させようとしていないか

## 4. AIへの依頼文を書く

AIに頼むときは、いきなり実装させません。まず、仕様の理解、修正方針、追加すべきテストを出してもらいます。

次のテンプレートを埋めてください。

````markdown
あなたはペアプロ相手です。
GitHub Issue #1 の修正方針を考えたいです。
まず実装せず、仕様の理解、不明点、修正方針、追加すべきテスト、PRで説明すべき点を出してください。

## GitHub上の文脈

- Issue:
- 対象ファイル:
- 既存テスト:
- 完了条件:

## 目的

研究室・サークルの差し入れeギフトを、予算、在庫、好み、避けたいカテゴリに合わせて1つおすすめしたい。

## 制約

- 外部API連携、個人情報保存、AIによる自由文メッセージ生成は今回の範囲外
- 予算内、在庫あり、避けたいカテゴリ以外、好みタグ1つ以上一致のギフトだけを候補にする
- 好みタグの一致数が多い順、一致数が同じなら安い順に選ぶ
- 候補がなければ `おすすめできるギフトがありません` を返す
- 差分は `src/giftRecommendation.js` と `test/giftRecommendation.test.js` に限定する

## 期待する出力

- 仕様の理解
- 不明点
- 修正方針
- 追加すべきテスト
- PRでレビューしてほしい観点
````

## 5. Plan Gateを行う

AIが修正計画を出したら、実装に進めてよいかを人間が判断します。これをPlan Gateと呼びます。

チェックリスト:

| 観点 | 見ること |
|---|---|
| 目的 | Issue #1 の目的とずれていないか |
| 範囲 | 変更対象を広げすぎていないか |
| 制約 | 予算、在庫、避けたいカテゴリ、好みタグ一致、同点時の安い順を扱っているか |
| テスト | バグ再現、予算、在庫、避けたいカテゴリ、好みタグ一致数、同点時の安い順が含まれているか |
| 範囲外 | 外部API、個人情報保存、自由文生成を勝手に追加していないか |
| GitHub | PR説明、CI、Review観点まで考えられているか |

判断メモ:

```markdown
判断: 進めてよい / まだ進めない

理由:

追加で確認したいこと:
```

## 6. Pull Request #2 を読む

PR #2:

https://github.com/giftee/ritsumeikan-ai-seminar/pull/2

このPRは、講師が用意したレビュー用のPRです。GitHub Actionsのテストは通っています。ただし、完全な模範解答として読むのではなく、チームとして受け入れてよいかを判断します。

見る順番:

1. Conversation
2. Checks
3. Files changed

### Conversationで見ること

| 観点 | 見ること |
|---|---|
| Issue連携 | `Closes #1` でIssueと紐づいているか |
| 変更理由 | なぜ直す必要があるかが書かれているか |
| 確認方法 | `npm test` やGitHub Actionsで何を確認したかが分かるか |
| レビュー観点 | レビュアーが何を見るべきかが書かれているか |
| 不安点 | 残っている不安や範囲外が説明されているか |

### Checksで見ること

GitHub Actionsの `test` が成功しているかを確認します。

ただし、CIが通っていることは「十分にレビューできた」という意味ではありません。CIは、書かれているテストを実行するだけです。必要なテストが足りなければ、CIが通っていても仕様漏れは起きます。

### Files changedで見ること

| ファイル | 見ること |
|---|---|
| `src/giftRecommendation.js` | Issueの仕様どおりに候補を絞り、並べ替えているか |
| `test/giftRecommendation.test.js` | 完了条件を確認するテストが追加されているか |

確認メモ:

```markdown
## 実装差分で確認したこと

## テスト差分で確認したこと

## 足りないと思ったこと
```

## 7. Reviewコメントを書く

あなたがレビュアーなら、どんなコメントをしますか。GitHub Reviewとして書くつもりで書いてください。

```markdown
### 良いと思ったこと

### 確認したいこと

### 追加してほしいこと

### 判断

Approve / Request changes
```

コメント例:

```markdown
好みタグの一致数で並べ、同点時に安いギフトを選ぶ方針はIssue #1の目的と合っています。
PR本文にも、外部API連携や自由文生成を今回の範囲外にした理由が書かれていて、差分も小さく追いやすいです。

一方で、「避けたいカテゴリは好みに合っていても候補にしない」ケースがテスト差分から読み取りづらいです。
`excludedCategories = ["convenience_store"]`、除外カテゴリのギフト `コンビニスイーツ`、代替候補 `カフェチケット`、期待値 `カフェチケット` のテストを追加してからApproveしたいです。

判断: Request changes
```

## 8. Learnを残す

最後に、次回AIに依頼するときに必ず伝えたいことを1つ書いてください。

```markdown
## 次回からAIに必ず伝えること

-
```

例:

```markdown
## 次回からAIに必ず伝えること

- 推薦ロジックでは、好みに合うことだけでなく、予算、在庫、避けたいカテゴリ、同点時の決め方をテストで確認してもらう。
```

## 任意: ローカルで試す

当日のハンズオンでは必須ではありません。余裕がある人だけ進めてください。

前提:

- Node.js 22系
- npm
- Git

セットアップ:

```bash
git clone https://github.com/giftee/ritsumeikan-ai-seminar.git
cd ritsumeikan-ai-seminar
npm install
npm test
```

画面を起動:

```bash
npm run dev
```

ブラウザで開く:

```text
http://127.0.0.1:5173/
```

発展課題として自分でブランチを作る場合:

```bash
git switch -c your-name/lab-gift-recommendation
```

変更後は `npm test` で確認してから、CommitやPull Request作成に進んでください。

## 持ち帰りチェックリスト

AIにコードを書かせる前:

- 目的を説明した
- GitHub Issueや関連ファイルを渡した
- 守るべき制約を書いた
- 今回やらないことを書いた
- まず実装せず、修正方針とテスト方針を出すよう依頼した

PRを見るとき:

- Issueと紐づいている
- 差分が小さい
- PR本文に「何を変えたか」「なぜ変えたか」「どう確認したか」がある
- GitHub Actionsが通っている
- 必要なテストが足りている
- ユーザーに見える結果として妥当
- 次回AIに渡す学びが残っている

## 今日のまとめ

AIはコードを書く速度を上げます。ただし、目的、制約、確認方法、チームとしての判断は自動では持ちません。

GitHubのIssue、Pull Request、Checks、Files changed、Reviewを使うことで、AIの出力をチームが判断できる成果に変えられます。

今日持ち帰ってほしいこと:

> AIに手続きを渡す。判断は人間が持ち、GitHub上でチームが判断できる形にする。
